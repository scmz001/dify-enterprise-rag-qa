# 星辰科技企业制度问答系统（Dify 版）

## 一、项目简介
基于 Dify 的低代码 RAG 应用，相比 Streamlit 版增加了：
- 多轮对话支持
- 关键词提取节点
- 混合检索 + Rerank
- 100 条分层自动化评测体系

## 二、架构

Chatflow 节点流程：

```
用户输入
   ↓
关键词提取（GLM-4-9B）
   ↓
知识检索（混合检索：语义 0.7 / 关键词 0.3，Top-K=6，阈值 0.4）
   ↓
代码节点（判断 result 是否为空，输出布尔值 has_result）
   ↓
条件分支（has_result 是否为 true）
   ├── true  → 模板转换 → 回答生成（qwen2.5-14b）
   └── false → 固定拒答（不调用模型）
                 ↓
               输出
```

| 节点 | 作用 | 说明 |
| --- | --- | --- |
| 用户输入 | 接收问题，进入 Chatflow | — |
| 关键词提取 | 从问题中抽取检索关键词 | 模型 GLM-4-9B |
| 知识检索 | 召回相关文本块 | 混合检索，语义 0.7 / 关键词 0.3，Top-K=6，阈值 0.4 |
| 代码节点 | 判断 result 是否为空 | 输出布尔值 has_result
| 条件分支 | 按 `result` 是否为空分流 | 空走拒答分支，非空进入生成 |
| 回答生成 | 依据检索结果作答 | 模型 qwen2.5-14b |
| 输出 | 返回答案与引用来源 | — |

## 三、Dify 配置
- 知识库：14 份文档，通用分块（\n\n，1024 字，重叠 100 字）
- 模型：模型 qwen2.5-14b（回答）、GLM-4-9B（关键词提取）
- 检索：混合检索，语义 0.7 / 关键词 0.3，Top-K=6，阈值 0.4
- 无 Rerank（曾配置 Qwen3-Reranker-8B，因 rerank-adapter 返回假分而放弃）

## 四、评测体系
- test_cases.csv：100 条分层测试集
- scripts/run_evaluation.py：自动化评测脚本
- results.xlsx：**当前**一次运行的结果，每次运行覆盖
- results/：历史归档。每次运行前，上一份 `results.xlsx` 会被自动移入此目录，
  命名为 `results_<时间戳>_<版本号>.xlsx`（版本号取自 `.env` 的 `APP_VERSION`，未设置则省略）。
  加 `--no-archive` 可跳过归档。

**对比历次效果时看 `results/` 里的时间序列，不要看根目录的 `results.xlsx`**——后者只有最新一次，
每次运行都会覆盖。归档目录里的文件按时间递增，可直接横向比对。脚本每次运行还会在终端打印
「本次 vs 上次」的摘要，含总通过率、分类型通过率、回归项（上次通过→本次失败）和改进项（上次失败→本次通过）。

### v0.9（2026-10-12）同一输入两次结果不同

**现象**：同一问题、同一知识库、同一模型，连续两次调用返回不一致的结果。

评测用例第 10 题「绩效考核结果 S/A/B/C 的强制分布比例是多少？」的两次实测：

| 轮次 | 检索来源 | 模型回答 | 判定 |
| --- | --- | --- | --- |
| 第 1 次 | 绩效考核与晋升制度.md | 完整答出 S(卓越) 前 10%、A 10%-30%、B 30%-70%、C 后 10% | 通过 |
| 第 2 次 | 绩效考核与晋升制度.md | 「根据公司现有制度，无法确认该信息，请联系HR或者IT服务台。」 | 未通过 |

**定位**：不是检索问题。两次都命中了正确文档，文档里明确写有强制分布比例，问题出在生成阶段——模型在资料齐备的情况下仍然拒答。这是**误拒答**，与防编造机制要处理的方向正好相反。

**影响**：单次评测的通过率不能当作稳定指标。

**处理**：在 Dify 应用配置中把 temperature 调至 0。连跑 4 次，第 10 题 4/4 通过；token 消耗从波动（930/778）收敛到稳定（657/657/662）。

**复现方式**：`python scripts/run_evaluation.py --limit 10`

### v0.10（2026-10-12）修复 Chatflow 变量报错

**现象**：评测中 28 条请求返回 HTTP 400，报错信息为：
```
Run failed: Variable #1791738139021.output# not found
```

**定位**：条件分支的"空/非空"判定对空数组失效——Dify 把 `[]` 判为"非空"，导致检索为空时仍走向回答 LLM 分支，而回答 LLM 引用的变量不存在。

**处理**：
1. 在条件分支前加代码节点，判断 `result` 数组是否为空，输出布尔值 `has_result`
2. 条件分支改成判断 `has_result == false`
3. **删除 `知识检索 → 回答LLM` 的直接连线**（关键：这条线绕过了条件分支，导致 ELSE 分支下回答节点仍被执行）
4. 交换 IF/ELSE 的连线方向

**结果**：28 条 HTTP 400 全部消失，拒答题从 40% 提升到 100%。

### v0.15（2026-10-13）文档规范化处理

**背景**：检索日志显示，即使换了通用分块，"标题块"和"正文块"仍被 `\n\n` 切成两块，导致 `content` 只有标题、没有正文。

**处理（三轮）**：
1. **第一轮**：用 AI 工具将 14 份原始文档统一转为 Markdown，修正 OCR 错误、统一全角标点、规范化标题层级
2. **第二轮**：删除 H2/H3 标题与其下方第一行正文之间的空行（66 处）
3. **第三轮**：删除"引导句（冒号结尾）+ 列表"之间的空行（32 处）

**验证**：
- 非空行差异为 0（只删空行，不改文字）
- 66/66 个 H2 标题后紧贴正文
- 所有列表引导句与列表项合并为同一语义单元

**结果**：
- 总通过率从 91% 提升到 97%，+6pt
- 对比题 70% → 100%
- 拒答题 95% → 100%
- 诱导题 90% → 100%
- 上轮 6 条"标题与正文分离"导致的失败全部修复（#33 #48 #51 #54 #55 #72）
- 剩余 3 条失败中，2 条非 RAG 问题（#91 API契约、#93 测试设计），1 条为跨文档语义混淆（#47）
- 真实 RAG 能力约 99%

### 关键经验

1. **模型选型**：非推理模型（qwen2.5 系列）在 RAG 场景优于推理模型（qwen3.5），延迟低且无"思考 token 耗尽"问题
2. **分块策略**：短章节文档用通用分块（`\n\n`），不要用父子分块；"标题 + 正文"必须紧贴，否则检索会命中空标题
3. **评测标准**：关键词匹配要归一化 + 分层降级；拒答题要行为判定，不能只看关键词
4. **Chatflow 连线**：条件分支的 IF/ELSE 必须严格对应，多余的直接连线会绕过分支逻辑
5. **Prompt 示例**：不能抄测试集内容，否则是过拟合而非泛化
6. **温度设置**：事实性问答场景 temperature 必须为 0，否则单次结果不可复现

## 六、与 Streamlit 版的对比

| 维度 | Streamlit 版 | Dify 版（本项目） |
| --- | --- | --- |
| 部署方式 | 本地 Python 进程，`.venv` + `streamlit run app.py`；模型由 LM Studio 的 Local Server 提供 | Dify 平台（http://localhost/v1）承载应用与知识库；本地模型经 OpenAI 兼容接口接入 |
| 编排方式 | 代码编排，用 LangChain 串联「检索 → 拼装 Prompt → 生成」 | 可视化 Chatflow，节点连线配置，调整流程不用改代码 |
| 多轮对话 | 不支持，每轮独立问答（界面仅展示消息记录） | 支持，上下文由 Chatflow 会话变量维护 |
| 检索策略 | 纯向量相似度（ChromaDB + bge-m3），阈值 0.55，TOP_K=4 | 混合检索（语义 0.7 / 关键词 0.3），Top-K=6，阈值 0.4，无 Rerank |
| 评测方式 | 人工验收：`--demo` 跑四个验收问题 + 界面抽查 | 100 条分层测试集 + `scripts/run_evaluation.py` 自动跑分，输出 `results.xlsx` |
| 模型切换 | 改 `.env` 中的模型名并重启进程，需在 LM Studio 侧换载模型 | 在 Dify 界面切换模型或改 provider 配置，即时生效，不动代码 |

各有取舍：Streamlit 版的检索、阈值、Prompt 全部在代码里，改动需重新部署，但逻辑透明、便于逐行调试；Dify 版编排和调参都在界面上，迭代快，代价是流程细节沉在平台配置里，不如代码直观，排查问题要回到 Chatflow 视图。

## 七、未完成项与取舍

原始规划有 5 个阶段，实际交付情况：

| 阶段 | 状态 | 说明 |
| :--- | :--- | :--- |
| 一、平台迁移 | ✅ 完成 | Streamlit → Dify |
| 一、数据扩展 | ❌ 未做 | 仍为 14 份文档，未扩到 50-80 份 |
| 二、多轮对话 | ❌ 放弃 | Dify 内置记忆强制注入 sys.query，污染生成；评估后判断单领域场景收益有限 |
| 三、Rerank | ❌ 放弃 | rerank-adapter 返回假分（全 0.5），改用混合检索权重模式 |
| 四、100 条评测 | ✅ 超额完成 | 6 类 100 条，脚本经历 3 轮迭代 |
| 五、成本估算 | ⚠️ 半完成 | 有 token 数据，未做单次/月度预估 |

**两个主动放弃的决策依据**：

1. **多轮对话**：Dify 内置记忆无法关闭对下游节点的强制注入，自建会话变量成本高于收益。单领域问答用户大多问一次就结束，追问占比低。
2. **Rerank**：本地 rerank 服务不可用，云端 Rerank 会引入数据出内网的合规风险。混合检索的关键词权重模式是等效降级方案。

## 十、成本分析

100 条测试共消耗 109,837 tokens，均值 1109 tokens/条。

**本地部署（当前方案）**：边际成本为 0，只有硬件摊销。
**若换 DeepSeek API**：
- 输入 1 元/百万 tokens，输出 2 元/百万 tokens
- 单次问答约 0.0015 元
- 1000 次约 1.5 元
- 月度（按日均 100 次）约 4.5 元
